# 翻译引擎速度与质量对比

用于在速度和质量之间选择分批翻译引擎。重跑方法见文末。

## 2026-10-05 第一轮

**条件**
- 样本：F04（MSTAN，`4LW4ETNL`）MinerU 文本的前 121 句（摘要、引言、数据分析段），带该篇已有的术语表。
- 并发：每个引擎都是 8 个同时请求，按现行分批规则（每批不超过 2600 字符）。
- 运行方式：引擎逐个依次运行，没有其他翻译任务同时占用 CPA。
- 渠道：`api:` 走本机 CLIProxyAPI（`http://127.0.0.1:8317/v1`），`grok::medium` 是插件里的 Grok Build 引擎（本机 grok CLI，思考强度 medium）。
- 质量评分：随机抽 30 句，7 个译文打乱后用字母盲评，1–5 分。
  - 5：准确、通顺、术语对。
  - 4：小的措辞问题。
  - 3：一处实质错误或明显别扭。
  - 2：部分意思错或漏。
  - 1：错译或未译。

| 引擎 | 用时（秒） | 句/分钟 | 请求数 | 失败句 | 检查后重试 | 质量均分 | 5 分占比 | ≤3 分占比 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| api:kimi-for-coding-highspeed | 14 | 514 | 7 | 0 | 0 | 4.80 | 80% | 0% |
| api:grok-4.7-build-fast | 26 | 275 | 7 | 0 | 0 | 4.90 | 90% | 0% |
| api:claude-haiku-4-5 | 28 | 258 | 8 | 0 | 3 | 4.70 | 70% | 0% |
| api:claude-sonnet-5-5（low） | 28 | 258 | 8 | 0 | 1 | 4.87 | 87% | 0% |
| grok::medium（Grok Build CLI） | 87 | 83 | 8 | 0 | 3 | 4.93 | 93% | 0% |
| api:k3-256k（low） | 90 | 81 | 7 | 0 | 0 | 4.83 | 87% | 3% |
| api:k3-256k（medium） | 114 | 63 | 7 | 0 | 0 | 4.80 | 83% | 3% |

“检查后重试”是返回结果没通过检查（引用编号、行内公式、漏句、未译）而重发的次数，最终都补齐了。

**结论**
- **质量差别很小。** 7 个引擎都在 4.7–4.93 分，30 句里只差 3–7 个“4 分”，单人评分下不能据此分高下。
  - 低分集中在措辞：“在 RNN 中得到了更好的学习”这类直译句式，以及“每一个单一步骤”“预测步长”这类不准确的术语（应为“预测步”）。
  - 没有引擎出现错译或漏译。
- **速度差别很大，选择主要看速度和额度。**
  - kimi-for-coding-highspeed 最快（约 500 句/分钟，整篇 400 句不到 1 分钟）。
  - grok-4.7-build-fast 次之，质量分数最高的一档，速度约为 k3-256k 的 3.4 倍。
  - k3-256k 在 8 并发下约 80 句/分钟。此前 16 并发、low 实测约 280 句/分钟，提高并发能部分弥补。
- **建议**：日常分批翻译用 CPA 的 grok-4.7-build-fast 或 kimi-for-coding-highspeed，并发 8–16；k3-256k 作为省额度的备选。Agent CLI（Grok Build）没有速度优势，留给需要 Agent 能力的整篇翻译。

**局限**
- 只测了一篇论文的 121 句，每个引擎只跑一次，网络和服务端负载会影响用时。
- 质量由一个评分者（Claude Opus）盲评，评分者与 claude 系列候选同源，可能有偏好。
- 各模型在 CPA 背后的额度和费用不同，表中不含成本。

**渠道说明**：表中除“grok::medium”外都是 API 调用（经本机 CLIProxyAPI）；grok::medium 是本机 Grok Build 命令行。七个都是**分批翻译**（与插件“翻译全文”相同：按段落分批，每批一次请求），不是整篇交给 Agent。

## 2026-10-05 第二轮：Claude 不同思考强度、Codex

条件同第一轮：同样 121 句，每个引擎同时 8 个请求，分批翻译，盲评抽同样的 30 句，评分标准不变。

- `claude:` 是本机 Claude Code 命令行（`claude -p`），模型写完整 ID `claude-sonnet-5-5`，不经过档位映射。
- `api:` 走本机 CLIProxyAPI。
- `codex::` 是 Codex 命令行，用其默认模型 gpt-6-astra。

| 引擎 | 用时（秒） | 句/分钟 | 检查后重试 | 质量均分 | 5 分占比 |
| --- | ---: | ---: | ---: | ---: | ---: |
| claude 命令行 sonnet-5-5（high） | 12 | 601 | 0 | 4.90 | 90% |
| claude 命令行 sonnet-5-5（medium） | 13 | 559 | 0 | 4.83 | 83% |
| claude 命令行 sonnet-5-5（low） | 22 | 324 | 4 | 4.93 | 93% |
| api sonnet-5-5（medium） | 26 | 275 | 0 | 4.87 | 87% |
| api sonnet-5-5（high） | 29 | 253 | 0 | 4.87 | 87% |
| codex gpt-6-astra（medium） | 44 | 166 | 0 | 4.90 | 90% |
| codex gpt-6.1-sol（low） | 44 | 166 | 0 | 4.90 | 90% |
| codex gpt-6-astra（low） | 49 | 147 | 0 | 4.93 | 93% |
| codex gpt-6-astra（high） | 51 | 144 | 0 | 4.97 | 97% |

所有配置都是 0 失败。

**结论**
- **思考强度对翻译几乎不起作用。** 同一模型低、中、高三档的质量分差在 0.1 以内，用时也没有随强度增加。
  - 翻译这类任务模型基本不需要深入思考。
  - Claude 命令行“低”档在这一轮最慢。按高、中、低倒序复测：高 291、中 594、低 560 句/分钟，变成排在第一组的“高”最慢。
  - 所以慢的是每轮第一组：冷启动、服务端预热，还有个别检查后重试。和思考强度无关。
  - 以后比速度应先空跑一组预热，或者打乱顺序多跑几次取中位数。
  - 默认用 low 或 medium 即可。
- **Claude 命令行比同模型的 API 快一倍以上。** 约 560–600 句/分钟，API 约 250–275。原因是命令行直连官方服务，API 要经过本机 CLIProxyAPI 转发。代价是占用 Claude Code 的订阅额度。
- **Codex 速度中等**（约 150–170 句/分钟），质量分最高的一档。gpt-6-astra 和 gpt-6.1-sol 没有差别。
- **两轮合起来看**：
  - 质量：所有引擎都在 4.7–4.97 分，没有错译或漏译。
  - 最快的一档：Claude 命令行（约 600）、kimi-for-coding-highspeed（约 500）。
  - 其次：grok-4.7-build-fast、sonnet API（约 250–275）。
  - 再次：Codex（约 150–170）。
  - 最慢：Grok Build 命令行和 k3-256k（约 60–80）。
  - 按自己哪边额度宽裕来选即可。

## 整篇交给 Agent（2026-10-04 实测，供对照）

同一篇 F04（MSTAN，468 句），Agent 一次性完成术语表、全文翻译、自查和报告。

| 方式 | 用时 | 折合句/分钟 |
| --- | ---: | ---: |
| Codex（gpt-6.1-sol，low） | 6.3 分钟 | 约 74 |
| Grok Build（grok-4.6，medium） | 8.5 分钟 | 约 55 |
| 用户自己的 Agent 会话（高强度） | 15 分钟（术语表 2、翻译约 6、自查和报告约 7） | 约 31 |
| 对照：Grok Build 分批（medium） | 约 4 分钟 | 约 120 |

- 整篇方式比分批慢，主要慢在单个会话串行处理和最后的自查、写报告。
- 质量上，整篇方式全文由同一个会话处理，用词更统一。分批方式靠“本篇术语表”弥补，上表的盲评中术语一致性没有出现明显问题。
- 整篇方式没有做盲评打分，用时数据来自当时的单次实测。

## 重跑方法

```bash
npm run build:cli
# ZBR_API_BASE / ZBR_API_KEY 指向 CPA；NO_PROXY='*' 避免本机代理
node tools/zbr.mjs bench --key <附件key> --limit 120 --concurrency 8 --out dev/out/bench \
  --engines "api:k3-256k:low,api:grok-4.7-build-fast,grok::medium"
python tools/bench-blind.py sample dev/out/bench 30   # 生成 blind.md 与 blind-key.json
# 按 blind.md 打分写 blind-scores.json：{"<句子id>": {"A": 5, "B": 4, ...}}
python tools/bench-blind.py score dev/out/bench       # 揭盲，写 quality.csv
```

引擎写法：`api:<模型>[:<思考强度>]`，或 `grok|codex|claude:[模型][:思考强度]`。bench 不写翻译缓存。
